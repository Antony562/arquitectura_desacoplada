01 / Los fundamentos

Primero, entendamos las piezas.

Un vocabulario compartido ayuda a ver qué cambia cuando una aplicación deja de ser una sola pieza.

01

Arquitectura de software

Es el plano que define las partes de un sistema, sus responsabilidades y la forma en que colaboran. Como el diseño de una ciudad: organiza edificios, calles y servicios.

En una tienda: catálogo, carrito y pagos tienen responsabilidades distintas.
02

Arquitectura desacoplada

Reduce las dependencias directas entre componentes. Cada parte conoce un contrato, no los detalles internos de las demás; así puede cambiar sin arrastrar todo el sistema.

Ejemplo: cambiar el proveedor de correo sin rehacer el registro.
03

Microservicios

Son servicios pequeños y autónomos, organizados alrededor de capacidades del negocio. Cada uno puede desarrollarse, desplegarse y escalarse de forma independiente.

Ejemplo: el equipo de pedidos publica cambios sin desplegar pagos.
04

¿Cómo colaboran?

El cliente envía una solicitud al API Gateway. Este la dirige al servicio responsable; otros servicios pueden colaborar mediante APIs o eventos. Cada servicio conserva su lógica y, cuando conviene, sus propios datos.

05

Monolito y microservicios

Monolito

Una aplicación desplegable, con módulos que suelen compartir proceso y datos.

Microservicios

Varios servicios desplegables por separado, coordinados mediante contratos.

No existe un ganador universal: depende del tamaño, el equipo y los requisitos del producto.

04 / Decidir con criterio

Autonomía con responsabilidad.

Distribuir una aplicación también distribuye sus retos. Evalúa el costo operativo junto al beneficio técnico.

CUANDO ENCAJA

Ventajas

  • Escalabilidad independienteAsigna recursos según la demanda de cada servicio.
  • Mantenimiento focalizadoCambia o despliega componentes sin publicar toda la aplicación.
  • Libertad tecnológicaElige herramientas adecuadas para cada capacidad, con criterio.
  • Mejor aislamiento de fallosUn problema puede limitarse si existen límites y resiliencia.
  • Equipos autónomosVarios equipos pueden entregar valor en paralelo.
LO QUE EXIGE

Desafíos

  • Complejidad de diseñoDefinir límites de servicio correctos es difícil y evoluciona.
  • Comunicación distribuidaHay que gestionar contratos, reintentos y tiempos de espera.
  • Observabilidad necesariaSeguir una solicitud entre servicios requiere trazas y métricas.
  • Latencia y consistenciaLa red y los datos distribuidos añaden decisiones y compromisos.
  • Más operaciónDespliegues, seguridad e infraestructura demandan disciplina.

Una regla útil: empieza por el problema del negocio. Para un producto pequeño o un equipo reducido, un monolito modular puede ser más simple y eficaz.
